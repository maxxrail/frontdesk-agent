# 7. SQLAlchemy 2.1 async, psycopg 3 and Alembic

- Status: accepted
- Date: 2026-11-12

## Context

The API is async, so the data layer should be too. Migrations need a tool
that can diff models against the database, and the app, migrations, seed
script and tests should all share one connection URL.

## Decision

- **SQLAlchemy 2.1** with the async engine, typed `Mapped[...]` models, and
  `mypy --strict` over the whole data layer.
- **psycopg 3** as the driver (`postgresql+psycopg://`). It supports both
  async and sync use with the same URL, which Module 0's settings and compose
  file already used, so no configuration changed. asyncpg is faster, but this
  service waits on an LLM for seconds per request; driver speed is not
  the bottleneck.
- **Alembic** for migrations. `migrations/env.py` takes the URL from the
  app's settings, never from `alembic.ini`, so there is one source of truth.
  A constraint naming convention makes autogenerated migrations
  deterministic.
- The engine is created in the app's lifespan, not at import. The app starts
  without a database, and `/readyz` reports one that is down (503) while
  `/healthz` stays 200, so an outage does not make the orchestrator restart
  healthy containers in a loop.

## Consequences

- Autogenerate does not drop Postgres enum types on downgrade. Migration
  0001 drops them by hand, and the round-trip test checks they are gone.
- `alembic check` runs in CI and in the test suite, so a model change
  without a migration fails the build.
- Migrations ship inside the Docker image, so the artifact that serves
  traffic is also the one that migrates its database.
